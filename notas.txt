Sobre React Query — tu intuición va bien encaminada, te la afino:

No es solo optimización de consultas — es un reemplazo completo de cómo manejás el estado de datos que vienen de un servidor. Hoy, sin React Query, cuando hacés una petición tenés que manejar manualmente:

- ¿Está cargando? → necesitarías un useState(loading)
- ¿Hubo error? → necesitarías un useState(error)
- ¿Los datos llegaron? → necesitarías un useState(data)
- ¿Necesito volver a pedir los mismos datos en otro componente? → tendrías que repetir todo esto

React Query te da todo eso ya resuelto, más:

- Cache automático (si ya pediste los proyectos, no los vuelve a pedir de la nada)
- Revalidación automática (si volvés a la pestaña, refresca datos viejos solo)
- Estados de loading/error listos para usar sin armarlos vos

export default function DashboardView() {
  // 3 estados separados que useQuery te da en 1 solo hook
  const [data, setData] = useState<Project[]>([]);
  const [isLoading, setIsLoading] = useState(true);
  const [isError, setIsError] = useState(false);

  useEffect(() => {
    // Función async DENTRO de useEffect (useEffect no puede ser async directamente)
    const fetchProjects = async () => {
      try {
        setIsLoading(true); // REACT-QUERY: LO TRAE HECHO isLoading
        const projects = await getProjects();//REACT-QUERY LO TRAE HECHO queryFn
        setData(projects); //REACT-QUERY LO TRAE HECHO data
      } catch (error) {
        setIsError(true);//REACT-QUERY LO TRAE HECHO error
      } finally {
        setIsLoading(false);
      }
    };

    fetchProjects();
  }, []); // ← array vacío = "ejecutá esto SOLO al montar el componente"//REACT-QUERY LO TRAE HECHO queryKey, parecido pero no tal cual-- 

  if (isLoading) return "cargando...";
  if (isError) return <p>Error al cargar</p>;
  
  return (/* JSX con data.map(...) */);
}

 * ═══════════════════════════════════════════════════════════════

 * CAPA 0 — Contrato de datos (ANTES de escribir cualquier código)
 * ─────────────────────────────────────────────────────────────
 * 1. Schema con Zod (frontend) → la forma que ESPERO recibir de la API
 * 2. Type derivado del schema (z.infer) → para que TS me ayude
 * 3. Types "recortados" con Pick/Omit según el caso de uso
 *    (crear ≠ editar ≠ mostrar, no siempre necesito los mismos campos)
 * POR QUÉ PRIMERO: todo lo que sigue se apoya en esta definición.
 * Si cambia después, TS avisa en cascada todo lo que rompe.
 *
 * CAPA 1 — Backend: modelo y reglas de negocio
 * ─────────────────────────────────────────────────────────────
 * 1. Model (Mongoose) → cómo se guarda en la DB
 * 2. Validaciones (express-validator) → qué formato acepta cada campo
 * 3. Controller → lógica de cada operación (create/read/update/delete)
 * 4. Middleware de pertenencia/autorización → ¿este recurso es del
 *    dueño/proyecto correcto? ¿tengo permiso?
 * POR QUÉ ANTES que las funciones de API: no tiene sentido apuntar
 * el frontend a un endpoint que no existe o no está validado.
 *
 * CAPA 2 — Funciones de API (frontend) — una por operación
 * ─────────────────────────────────────────────────────────────
 * getX(id) | getXById(id) | createX(data) | updateX(id,data) | deleteX(id)
 * REGLAS FIJAS:
 *  - Desestructurar { data } de axios, NUNCA retornar el AxiosResponse
 *    completo (rompe toast/UI — bug real que encontré en deleteProject)
 *  - try/catch con isAxiosError + throw new Error(...) → si no hago
 *    throw, el error NUNCA llega a onError de la mutación
 *  - Cuidado con el "else" faltante en el catch → si no es error de
 *    axios, igual hacer throw de algo, sino queda undefined silencioso
 *  - Si la respuesta es sensible a estructura (array, objeto anidado)
 *    → validar con Zod (safeParse) antes de retornar
 *
 * CAPA 3 — Conectar la API con React (React Query)
 * ─────────────────────────────────────────────────────────────
 * LEER (GET)            → useQuery
 *   - queryKey única y descriptiva: ['tasks', projectId], no solo
 *     ['tasks'] — si depende de una variable, va DENTRO del array
 * CREAR/EDITAR/BORRAR    → useMutation
 *   - mutationFn apunta a la función de API
 *   - onError → toast.error(error.message)
 *   - onSuccess → invalidateQueries de TODAS las queryKeys afectadas
 *     (a veces son 2: la lista Y el detalle)
 * POR QUÉ query≠mutation: GET es idempotente/cacheable, el resto
 * produce un efecto real cada vez → React Query los trata distinto.
 *

 * ─────────────────────────────────────────────────────────────
 * - react-hook-form con defaultValues (vacíos para crear, con data
 *   real para editar — mismo componente, distinto estado inicial)
 * - Validación básica (required, etc.) → primera barrera, solo UX
 * - El type del form suele ser un Pick del type completo
 *
 * CAPA 5 — Vistas / componentes que orquestan todo
 * ─────────────────────────────────────────────────────────────
 * 1. TODOS los hooks primero (Reglas de los Hooks)
 * 2. Guardas de datos DESPUÉS de los hooks (if !id, if isError,
 *    if isLoading) — nunca antes
 * 3. Render condicional según el estado de la query
 * 4. Acciones destructivas (eliminar) → SIEMPRE confirmación antes

 * ─────────────────────────────────────────────────────────────
